## 2. 三视角独立陈述

### 2.1 tech-lead 陈述（工程与架构视角）

**总立场：四项全部可采纳，工程风险低、复用面大，估算可信。**

1. **基建已就绪，增量成本低**。P0 所需的五块基建全部在 main 且经实测：①店铺可操作性口径 `EnsureStoreOperable`（R165 六处 P1 修复统一收敛，#332 已合入，R170 探针全绿）；②审计 fail-closed（`mcp_tool_call_logs`，R169 实测审计表不可用时 MCP `-32603` 拒绝、恢复自愈）；③三层限流含 Redis Lua 令牌桶 + 进程内降级（R169 实测 Redis 停机不 fail-open）；④token 治理全生命周期（创建/吊销/过期/purpose 隔离/每租户 20 上限并发安全，R169 全 PASS）；⑤permmatrix 契约测试框架（view-only sweep 30 探针常驻）。写白名单是在已验证的骨架上加五个工具面，不是新战线。
2. **工作量估算维持设计稿口径并细化**：P0 实现 2 轮（后端 1.5：scope 枚举演进 + 双开关 + dry_run/confirmationToken 状态机 + 五工具 handler + 限额 + 写审计字段；Admin/文档/测试 0.5：token 页写 scope 创建与流水视图、mcp.md/env.md/permission-matrix.md 同步）+ 安全验收 0.5 轮（提示注入/确认绕过/限额绕过/审计 fail-closed 实测 + Docker 全栈 E2E）。合计 **2.5 轮**。R170 给出的「1–1.5 轮」是仅计后端实现的口径，本材料以含验收的 2.5 轮为准（对老板报保守数）。
3. **测试面清单（实现轮的硬验收标准）**：
   - 契约层：每个新写路由进 `matrix.json` 且 readonly persona=forbid；新增「readonly token 调写工具全拒」MCP 契约测试；view-only/operator/跨租户三 persona × 5 工具探针。
   - 状态机层：dry_run 无 confirmationToken 不可 execute；参数哈希漂移拒绝；token 过期/复用拒绝；`already_executed` 幂等返回。
   - 闸门层：环境开关关/租户开关关/scope 缺失三层各自独立 403 实测；W5 无金额上限配置即不可用。
   - 限额层：30/时、200/日 边界 429；单次单对象强制。
   - 审计层：dry_run 与 execute 各一条且关联同一确认哈希；审计不可写时 execute 拒绝。
4. **技术反对意见的自我审查**：confirmationToken 引入了新的服务端状态（Redis/DB 存 TTL 5 分钟的一次性 token），是唯一新增的有状态组件——但复用现有 Redis，无新依赖，且失败模式是 fail-closed（token 丢失=重新 dry_run），可接受。

### 2.2 security-engineer 陈述（攻击者视角）

**总立场：同意立项，但把「不采纳时的诱惑路径」堵死比「采纳什么」更重要；D2/D3/D4 的严格形态是 D1 成立的前提，不可拆开讨价还价。**

1. **威胁模型排序（沿设计稿 §3.1，按 R165/R169 实测数据校准）**：
   - **LLM 参数幻觉是第一威胁**，不是 token 泄露。R165 审计发现的六处 P1 全部是「把可见当可操作」的权限缺口——人写的代码尚且如此，LLM 生成的参数（单号/金额/id）出错是常态而非异常。dry-run 强制两步 + 参数哈希绑定是唯一在协议层（而非 prompt 层）拦截幻觉的机制，**D3 不可降级为可选**。
   - **提示注入的现实边界要诚实**：P0 的「人确认」发生在 MCP 客户端侧，服务端无法证明确认者是人。因此限额（D4）不是锦上添花而是注入场景的**唯一硬兜底**——注入最多骗到一次 dry_run 提案 + 限额内的 execute。W5 金额上限必填（未配置即禁用）把最坏损失钉死在租户自己声明的数额内。
   - **token 泄露**：写 token 强制过期（30/90 天）+ 独立 scope 使泄露半径 = 五个站内标记工具 × 限额窗口，且流水视图让发现时间趋近实时。对比：若走「readonly token 加 allowWrite 旗标」方案，存量 20/租户 token 全部变成待排查对象——**D2 的独立 scope 是把泄露排查面从 O(存量) 压到 O(新发)**。
2. **对 W5 mark-paid 进 P0 的安全审查结论：有条件放行**。mark-paid 只改站内资金标记、不动真实资金；错误代价是对账差异（可作废纠正），与 W11 库存扣减（不可逆差异）有本质区别。三个不可妥协前提：①金额上限租户必填、fail-closed；②`pending_review`/`held` 订单关联的采购单拒绝（审单闸门优先级高于 MCP）；③审计必记金额摘要。三者任一被砍，则我方立场转为 W5 出 P0。
3. **operator 管理写 token：反对（这是本轮唯一真分歧点）**。理由：①写 token 创建 = 授予写面，属于治理动作，R159/R165 确立的口径是治理面永不下放；②operator 的店铺授权是动态的（可被收回 operate 授权），若其创建的写 token 不随授权收回而失效，就复刻了 R165 P1-6「可见当可操作」的缺口——要做对就必须引入「token 随创建者授权联动失效」机制，P0 不值得为此加复杂度；③admin 独占创建 + 流水视图对 operator 可见（只读），已满足「operator 用、admin 管」的分工。
4. **不采纳 D1 的安全机会成本（反直觉但必须说）**：需求已被 AutoDS 教育验证，若我方不提供受治理的写通道，用户会自行用「浏览器自动化 + admin 密码给 agent」的野路子（社区已有先例），那是**零审计、全权限**的影子写面。提供白名单写恰恰是收缩真实攻击面。

### 2.3 product-manager 陈述（用户价值与竞争视角）

**总立场：D1 全量采纳且 W5 必须进 P0；时间窗口是本决策最稀缺的变量。**

1. **竞品时钟**（R170 实测口径）：AutoDS Claude MCP 写操作 2026-07-16 发布 → 08-03 Q2 汇总列为主打 → 08-05 多店铺（eBay/Shopify/WooCommerce）单会话管理教程，「搜品→刊登→改价→报表」含写全链路进入**用户教育量产期**。店小秘/马帮仍为零（AI 布局在图片/内容生产侧）。这意味着：①「对话式写」的用户心智正在被竞品免费教育——我们收获需求验证；②但「MCP 写=账号全权直通」的心智也在被同步塑造——差异化窗口（「有治理的写」）每拖一个决策周期收窄一分。R151→R161→R170 三次复评对此项的措辞从「方向性信号」→「窗口收窄」→「第一优先决策项」，趋势明确。
2. **为什么 W5 必须进 P0（用户价值论证）**：P0 的目标场景是「采购协同的机械劳动交给 agent」——运营在 1688 人工下单后，对话式完成「回填单号(W3)→标记付款(W5)→回填运单(W4)」三连，这是一个完整闭环。砍掉 W5 则闭环断在中间，用户仍须切回 Admin UI 补一步，「对话式运营」退化为「对话式打标签」（W1/W2），演示价值 > 使用价值，P0 上线后的真实使用数据（P1 扩展的决策依据）会失真。W5 的限额前提（租户必填金额上限）同时是很好的产品化触点：配置动作本身让用户理解并信任治理模型。
3. **差异化叙事**：R170 第 15/16/17 项的超越判定全部押在安全治理（店铺级读写分权、自托管、安全工程体系）。「竞品有写但无治理、我方有写且有治理」是现成的第二层超越叙事；反之若照搬 AutoDS 直接刊登（D2 语境下的对齐派主张），等于自毁差异化且撞上「绝不自动外发」产品红线。
4. **不采纳的机会成本量化**：①身位——只读 MCP 的「超越」评级（R170 增项 19）依赖「竞品无 MCP」的对照面，AutoDS 已破坏该对照，维持只读则该项在下次复评大概率降为「达到」；②节奏——P1 扩展（W6–W9）与 out-of-band 确认收件箱均以 P0 审计数据为决策输入，P0 每晚一轮，后续整条写路线图顺延一轮以上；③用户——自托管目标用户（企业内分岗场景）恰是对「受治理写」付费意愿最高的人群。
5. **对过度工程的产品侧警惕（对 tech-lead 的预防性质疑）**：2.5 轮估算可接受，但要求实现轮严格按设计稿边界执行——不做批量、不做 out-of-band 收件箱、不做 token 绑定店铺清单，全部留给 P1 触发式。P0 范围蔓延是比安全风险更现实的交付风险。

### 3.2 围绕 D2（独立 `write:ops` scope）

| 质疑 | 回应 | 收敛 |
| --- | --- | --- |
| **PM → TL**：双 token（读一个、写一个）配置成本高，用户在 Claude Desktop 要配两条，体验差；能否 `write:ops` 隐含读？ | **TL**：scope 是集合语义，一个 token 可同时带 `readonly`+`write:ops`（一条配置）；**SE**：但「写默认含读」不可反向成立——保持「写不隐含读」使最小权限组合始终可表达（如只允许打标签、不允许查订单的自动化场景） | 采纳：创建页默认勾选组合 `readonly+write:ops`（体验），但底层 scope 独立（安全），文档写明 |
| **SE → TL**：scope 从单值到集合，存量鉴权代码是否有「未知值 fail-open」风险？ | **TL**：现状对非 `readonly` 的 scope 行一律按无效处理（`docs/mcp.md` 明文 + R169 实测），集合演进沿同一口径：未知成员忽略、已知成员校验、空集拒绝；permmatrix 加「畸形 scope 值全拒」用例 | 进实现轮测试面 |
| **TL → PM**：强制 30 天过期会不会造成「token 静默过期→用户以为产品坏了」的支持成本？ | **PM**：只读 token 已有「即将过期（≤7 天）」提示（`docs/mcp.md`），写 token 沿用并加流水视图入口即可；相比之下「永不过期的写 token」在自托管用户的安全审计中是硬伤 | 沿用既有过期提示机制，无新增设计 |

**D2 收敛：独立 `write:ops` scope，不隐含读、创建时授予、仅 admin、强制过期；创建页提供 `readonly+write:ops` 组合默认项弥补配置体验。**

### 3.3 围绕 D3（三层闸门 + dry-run→确认token→execute）

| 质疑 | 回应 | 收敛 |
| --- | --- | --- |
| **PM → SE**：每次操作都 dry_run→人读→execute，五连操作要十次往返，会不会把「对话式效率」优势磨没？AutoDS 是零确认直通 | **SE**：不可妥协——这正是与 AutoDS 的差异化本体，砍确认=变成 AutoDS 劣化版（他们还有平台直连）；**TL 补充**：MCP 客户端（Claude）本身会把 dry_run 预览渲染成一条消息，用户回一句「执行」即可，体感是「AI 先给我看再动手」，这在用户研究中是信任加分项而非摩擦 | 维持强制两步；PM 要求实现轮在 dry_run 返回结构中包含人类可读的一句话 summary 字段（降低阅读成本），采纳 |
| **TL → SE**：三层闸门中环境级 `MCP_WRITE_ENABLED` 默认 false，意味着 Docker 部署用户升级后功能不可见，会不会造成「做了等于没做」？ | **PM 代答**：这是发布策略而非缺陷——`.env.docker.example` 注释 + 版本公告引导显式开启，「安全默认关、一行开启」正是自托管用户期待的形态；对比 fail-open 的先例（无）不可开 | 维持默认关；发布物料（env.md/公告）进实现轮文档清单 |
| **SE → TL**：confirmationToken 若存 Redis，Redis 故障时行为？ | **TL**：token 校验不可达=拒绝 execute（fail-closed，与限流降级「不 fail-open」同哲学）；用户重新 dry_run 即可，无数据风险 | 进实现轮测试面（Redis 停机下 execute 必拒） |

**D3 收敛：三层默认关闭闸门 + 强制两步全部维持设计稿形态；新增 dry_run 人类可读 summary 字段与 Redis 故障 fail-closed 测试两项实现要求。**

### 3.4 围绕 D4（fail-closed 审计与限额 + operator 管理权 + 过期策略）

| 质疑 | 回应 | 收敛 |
| --- | --- | --- |
| **PM → SE**：不让 operator 建写 token，中型团队里 admin 会成为发 token 瓶颈，损害「运营自助」价值主张 | **SE**：见 §2.2 第 3 点——operator 授权动态性与 token 生命周期解耦会复刻 R165 P1-6 缺口模式；瓶颈论被数据削弱：token 是长效凭证（30 天），不是每日申请物 | **收敛为：P0 仅 admin 可创建/吊销；operator 对写流水视图有只读可见性；「operator 自助 + 授权联动失效」列为 P1 研究项**（PM 接受，SE/TL 一致） |
| **TL → SE**：写审计记参数摘要与只读「不记参数」口径相反，会不会带来敏感信息入审计库的新风险？ | **SE**：白名单式记录（仅金额/单号/id 类字段，设计稿 §3.5 已定），不记自由文本；写操作的参数就是证据链，不记才是审计缺口 | 维持；字段白名单进实现轮评审清单 |
| **SE → PM**：200/租户/日 的限额对真实运营够用吗？定太松失去兜底意义，定太紧用户骂 | **PM**：按 seed 演示数据口径（38 订单/日的演示租户），五工具合计日操作量级在几十次；200 是 5 倍余量，且租户可下调、服务端上限硬编码不可上调——方向正确。P0 上线后用审计数据复核，P1 再调 | 维持默认值；「限额校准」列入 P0 验收后复盘项 |

**D4 收敛：审计 fail-closed + 参数摘要白名单、四项限额默认值、仅 admin 管理写 token（operator 只读流水）、默认 30 天/上限 90 天/禁止永不过期——全部维持并细化。**

## 4. 每决策点终版材料（推荐 / 反对与反驳 / 竞品对照 / 工作量与测试面 / 不采纳机会成本）

### D1：P0 五工具白名单（含 W5 mark-paid）

- **推荐**：采纳 W1–W5 全量；W5 带 fail-closed 三前提（§3.1）。
- **主要反对意见及反驳**：
  - 「W5 涉资金，应降级 W1–W4」→ 反驳：W5 不动真实资金，错误可作废纠正；限额+确认+审计+审单闸门四重兜底；砍 W5 则采购闭环断链，P0 数据失真（§2.3-2）。降级预案保留为老板选项。
  - 「W2 刚出过 P1 缺口不该放」→ 反驳：R165 修复后 W2 是闸门最厚候选，回归测试常驻（§3.1）。
- **竞品对照**：AutoDS 实际写范围 = 导入/上传商品、**直接 publish 到 eBay/Shopify/WooCommerce**、改价与 listing 内容、批量跨店更新、fix listings（R170 复查 08-05 教程确认多店铺单会话管理已量产教育）。我方 P0 五工具全部站内标记/回填，**刻意不与其写范围对齐**——对齐即撞「绝不自动外发」红线且需尚未解锁的平台凭证。
- **工作量与测试面**：五工具约占 P0 后端 1.5 轮中的 0.7 轮（每工具 dry_run 预览+execute+审计+限额接线）；测试面见 §2.1-3（契约/状态机/闸门/限额/审计五层）。
- **不采纳机会成本**：对话式运营停留在演示级（W1/W2 打标）或完全缺位；增项 19「AI 助手入口」超越评级下次复评大概率降级；用户自行野路子接 agent 造成影子写面（§2.2-4）。

### D2：独立 `write:ops` scope

- **推荐**：采纳；不隐含读、创建时授予不可升级、仅 admin、强制过期；创建页提供组合默认项。
- **主要反对意见及反驳**：
  - 「readonly token 加 allowWrite 旗标更省事」→ 反驳：存量每租户至多 20 个只读 token 全部语义可疑化，泄露排查面 O(存量)→O(新发) 的优势丢失；违反 R152「存量攻击面不因新能力变宽」取舍原则。
  - 「双 token 配置体验差」→ 反驳：scope 集合语义一个 token 可组合（§3.2）。
- **竞品对照**：AutoDS 写能力直接继承账号 OAuth 全权限，无独立写 scope、无 token 治理公开机制——是社区批评的反面教材；Shopify 官方 agent 分层（敏感工具显式授予）与 ShopMCP（write scope 最小授予）均与我方同向。
- **工作量与测试面**：scope 枚举演进 + 创建页改造约 0.3 轮；测试面：畸形/空/未知 scope 全拒、readonly token 调写工具全拒契约、写 token 过期/吊销双入口失效（复用 R169 用例框架）。
- **不采纳机会成本**：若砍 D2 而保 D1，写权限只能挂在现有 token 模型上，R169 全绿的 token 治理叙事（第 17 项超越依据）被稀释；后续再拆独立 scope 需迁移存量，成本翻倍。

### D3：三层默认关闭闸门 + dry-run→确认token→execute

- **推荐**：采纳；环境/租户/token 三层全默认关；dry_run 必经、confirmationToken 参数哈希绑定 TTL 5 分钟单次使用、Redis 故障 fail-closed；dry_run 返回含人类可读 summary。
- **主要反对意见及反驳**：
  - 「两步确认磨损对话效率，竞品零确认」→ 反驳：零确认=放弃差异化本体；客户端渲染下体感为「先预览再执行」，是信任加分（§3.3）；限额内免确认模式已在设计稿明确列入不做清单（LLM 参数幻觉不因金额小而消失）。
  - 「默认关导致功能不可见」→ 反驳：自托管安全产品的正确默认；一行 env 开启，发布物料引导（§3.3）。
- **竞品对照**：AutoDS 无 dry-run/确认/限额公开机制；ShopMCP 三层闸门（平台 scope→产品总开关默认关→逐操作确认）是我方三层结构的直接对标物，行业已收敛；Weaverse「上限写进 schema 而非 prompt」原则由 confirmationToken 参数哈希实现。
- **工作量与测试面**：dry_run/execute 状态机 + confirmationToken 是 P0 最大单体，约 0.5 轮；测试面：无 token/过期/参数漂移/复用四类拒绝、`already_executed` 幂等、Redis 停机拒绝、三层开关独立 403。
- **不采纳机会成本**：若砍两步确认，安全模型退化为「限额内自动执行」，提示注入与参数幻觉均只剩限额一道兜底——security-engineer 视角明确表态该形态下应整体否决 D1；即 **D3 是 D1 的成立前提**，不存在「采 D1 砍 D3」的组合。

### D4：fail-closed 审计与限额 + operator 管理权 + 默认过期策略

- **推荐**：采纳；审计复用 fail-closed 口径且写操作记参数/结果摘要（字段白名单）；限额四项默认值（30/token/时、200/租户/日、单对象、W5 金额上限必填）；仅 admin 管理写 token，operator 只读流水视图；默认 30 天过期、上限 90 天、禁止永不过期。
- **主要反对意见及反驳**：
  - 「operator 应可自助建写 token」→ 反驳：operator 店铺授权动态性与 token 生命周期解耦会复刻 R165 P1-6「可见当可操作」缺口；正确做法（授权联动失效）复杂度不属于 P0——列 P1 研究项（§3.4，三方收敛）。
  - 「写审计记参数与只读口径不一致」→ 反驳：写参数即证据链，白名单式记录无敏感面（§3.4）。
  - 「强制过期增加支持成本」→ 反驳：既有 ≤7 天过期提示机制直接复用；永不过期写 token 是自托管审计硬伤。
- **竞品对照**：AutoDS 无公开审计/限额机制；我方审计 fail-closed（审计不可写即拒调用）经 R169 实测（`-32603` + 恢复自愈），在三竞品中无对标物，是第 16/17 项超越叙事的直接延伸。
- **工作量与测试面**：审计字段扩展 + 限额四项 + Admin 流水视图约 0.5 轮（含在 2.5 轮总数内）；测试面：审计不可写时 execute 必拒、dry_run/execute 配对落库、限额边界 429、operator 建写 token 403、过期边界（30/90/731 非法值）。
- **不采纳机会成本**：砍审计摘要=出事后无法回答「AI 改了什么」，治理卖点自我否定；砍限额=提示注入无硬兜底（§2.2-1）；放开 operator=治理面下放先例，与 R159 以来全部安全收口方向相逆。

## 5. 收敛结论与执行预案

1. **四项一致推荐采纳**（D1 含 W5、D2 独立 scope、D3 三层+两步、D4 严格治理），依赖关系：D3/D4 是 D1 的成立前提，D2 是 D4 的载体——**建议整体采纳或整体否决，唯一可独立降级项是 D1 的 W5**（降级为 W1–W4 不影响其余）。
2. **如无异议将按此执行**（CHARTER §3-4 提议即默认方案）：老板勾选后另开实现轮次，排期 = P0 实现 2 轮 + 安全验收 0.5 轮；实现轮硬边界 = 设计稿 §5 不做清单 + 本材料新增的验收标准（dry_run 四要素与 summary、service 层复用证明、Redis 故障拒绝、operator 403）。
3. **辩论新增、需回写设计稿的增量**（实现轮一并落地，不改本轮文档以外文件）：①W5 dry_run 预览四要素；②dry_run 人类可读 summary 字段；③创建页 `readonly+write:ops` 组合默认项；④「operator 自助 + 授权联动失效」列 P1 研究项；⑤限额校准列 P0 验收后复盘项。
4. **风险登记**：P0 上线初期最可能的用户反馈是「确认步骤繁琐」——预案为 P1 的 out-of-band 收件箱与限额校准均以真实审计数据触发，不预支实现（三方一致，防范围蔓延）。

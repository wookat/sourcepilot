# R188 线1：R187 性能审计 P2×4 收口（fullstack-engineer + performance-engineer）

日期：2026-08-08。收口 R187 线2 性能审计（`docs/progress/R187-line2.md`，PR #376）登记的 4 项 P2。

## 【结论】

P2×4 全部收口/登记：① `mcp_tool_call_logs` 补 `(tenant_id, created_at DESC)` 复合索引（AutoMigrate 迁移），110k 行下深分页 p50 20.6ms → 3.5ms，buffers 101k → 1.3k；② 异常聚合下推为 SQL 聚合（`SummaryOpenExceptions`），双租户 4 万行订单行规模下数值口径与旧内存路径完全一致，摘要延迟 p50 ~400ms → ~200ms 且不再整表物化；③ 前端首包预算门禁落地（`pnpm check:bundle-budget`，umi.js gzip ≤ 350kB / umi.css ≤ 20kB，当前 313.9kB / 5.9kB，CI node.yml 接入）；④ MCP 写配额计数口径登记不改（fail-closed 设计使然，约定见 `docs/mcp.md`）。全套本地门禁绿。

## 【改动】

1. **P2-1 复合索引**：`backend/internal/database/migrate_round188.go` 在 `database.AutoMigrate` 链内以 `CREATE INDEX IF NOT EXISTS idx_mcp_tool_call_logs_tenant_created ON mcp_tool_call_logs (tenant_id, created_at DESC)` 建索引（round122 同款模式，PostgreSQL-only、幂等、回滚 `DROP INDEX IF EXISTS`）。审计列表恒为租户过滤 + `created_at DESC` 分页，原单列 `created_at` 索引在深分页时按 tenant 过滤丢弃约一半行（EXPLAIN `Rows Removed by Filter: 50022`）。
2. **P2-2 SQL 聚合**：新增 `orderexception/summary_sql.go` 的 `SummaryOpenExceptions`，将 9 类异常的 open 计数下推为 SQL `COUNT`/条件 `SUM`（负毛利仍走有界收集器，两条路径共享同一 oracle）；标记排除以 `NOT EXISTS` 对 `order_exception_marks` 反连接（`::text` 显式转换保证命中 `ux_order_exception_mark_quad` 索引）；`AllowedShopIDs` 店铺范围、租户/平台/店铺/订单过滤逐收集器等价复刻。`DashboardSummary`（运营看板/大屏）与 readonlyquery `report_summary` 改走新路径；工作台列表 `ListOrderExceptions` 行为不变。
3. **P2-3 首包预算**：`scripts/check-bundle-budget.mjs` + `pnpm check:bundle-budget`，按 gzip 实测 admin/dist 入口文件（匹配内容哈希文件名），基线 320.6kB（R187），预算 350kB 留 ~9% 余量；`node.yml` admin job 在 `build:admin` 后执行。未做激进瘦身（任务口径）。
4. **P2-4 写配额口径（登记不改）**：配额刻意等同审计轨迹（成功 execute 行即消耗），任何「合成数据排除标记」都可被写入方伪造从而绕过限额，破坏 fail-closed 语义。约定合成审计数据必须把 `created_at` 写出配额窗口（见 `docs/mcp.md` R188 登记条目）；仓库内置 seed 工具不写 MCP 审计行。

## P2-1 `GET /api/v1/mcp/audit-logs` 写审计行最小暴露（代码收口）

R183 发现该端点无独立权限位，operator/readonly 可见全部写动作审计行（mode、paramsSummary、confirmHash、amount）。

收口口径（与「写 token 仅管理员可见」同一治理轴 `settings.manage`）：

- 端点对四角色仍返回 200（只读工具 / 开放 API 审计行保持四角色可读，不缩小既有只读可见面）；
- **写动作审计行（有 mode 的行，或工具在写白名单内的行）仅 `settings.manage` 持有者可见**，operator/readonly/reviewer 查询时在 SQL 层自动过滤，显式传 `mode=dry_run/execute` 也无法绕过；
- Principal 解析失败按非管理员处理（fail-closed）；
- 写白名单来源：`mcpserver.WriteToolNames()`（新导出，与 `isWriteTool` 同一注册面，注册测试保证两处一致）；
- admin UI 同步：非管理员隐藏「模式 / 参数摘要 / 确认哈希 / 金额」列与「调用模式」筛选、工具筛选不再列写工具分组。

## P2-3 读工具审计时序（评估结论：登记，不改代码）

评估 `mcpserver/server.go` 审计中间件：读工具审计行在工具执行**后**写入，但响应受 fail-closed 约束——审计写入失败则该次调用返回 `-32603` 且不返回数据，**不存在“数据已出、审计未落”的泄漏窗口**；读工具无副作用，进程在“执行后、审计前”崩溃时响应也未发出，无未审计的数据外泄。将审计提前到执行前会为失败调用留下歧义行（无法区分“尝试”与“完成”）且需双写，收益为负。结论：维持现状，登记理由（本节）。

## 1. MCP fail-closed 拒绝的 JSON-RPC error code 0 → -32603

- 问题：#303 引入的审计 fail-closed 用 `errors.New(...)` 拒绝调用，go-sdk `toWireError` 会把普通 error 包成 `WireError{Code: 0}`——JSON-RPC 2.0 中 0 不是合法的预定义错误码（规范错误码为 -32700/-32600/-32601/-32602/-32603 与 -32000~-32099 server error 段），客户端无法按码分类处理。
- 取舍：选 `-32603 internal error`（`jsonrpc.CodeInternalError`）。理由：审计库故障是服务端内部故障，不是请求本身的问题（排除 -32602）；MCP 规范对工具执行失败推荐用 result.isError 表达，但审计 fail-closed 是「协议层拒绝返回结果」，语义上就是 internal error；SDK 对 `*jsonrpc.Error` 原样透传，不需要自定义 -32000 段。
- 实现：`mcpserver.auditMiddleware` 返回 `&jsonrpc.Error{Code: jsonrpc.CodeInternalError, Message: "audit log unavailable, tool call rejected"}`；`TestAuditWriteFailureRejectsToolCall` 补断言：错误必须是 `*jsonrpc.Error` 且 code == -32603（回归验证：临时改回 code 0 时该测试失败）。
- 开放 API 侧口径核对：`openapi.audited` 审计 fail-closed 返回 HTTP 500 + envelope `code=50000`（`docs/open-api.md` §97 已登记），REST 侧本就是非零规范码，口径一致，无需改动。

## 2. R155 线2 P2 处置

### 2.1 `--pre-upgrade-check` 默认 /var/backups 非 root 不可写

- 评估：默认 `/var/backups` 面向 root 部署（生产部署脚本其余步骤也普遍需要 docker 权限），改默认路径（如 repo 内 ./backups）会把数据库备份落进代码目录、易被误删/误提交，不改默认。
- 处置：启动时清晰报错——`mkdir -p` 失败与目录不可写（新增 `[ -w ]` 检查，覆盖「目录已存在但属 root」场景，此前该场景会误报为「pg_dump 备份失败」）都立即以明确信息失败：提示当前用户、建议以 root 运行或 `BACKUP_DIR=<可写目录>` 覆盖。`docs/upgrade-guide.md` 同步说明。
- 实测：非 root 下 `BACKUP_DIR=/var/backups` 场景输出 `[deploy][失败] 无法创建备份目录 /var/backups（当前用户 ubuntu）：请以 root 运行，或用 BACKUP_DIR=<可写目录> 覆盖`。

### 2.2 Docker demo 库遗留 `e2e-refresh-verify` token 由 clean 覆盖核实

- 核实结论：**不覆盖**。`demoseed.Cleanup` 只删除 `mcp_api_tokens.name LIKE 'DEMO-%'`，`VerifyClean` 也只统计 DEMO- 行。Docker 实测：创建名为 `e2e-refresh-verify` 的 token → `seed:demo:full:clean` + `verify`（输出 zero DEMO- residual rows）后该 token 仍在库且未吊销。
- 处置：不扩大 clean 的删除面（按任意名删除有误删真实 token 风险）；本地 demo 库中的遗留 token 已手动删除；`.agents/skills/demo-fullstack-walkthrough/SKILL.md` 常见坑补充「非 DEMO- 前缀 token 需测试收尾自行吊销/删除」。
